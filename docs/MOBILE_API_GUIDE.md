# Vastukosh API — Mobile & Third-Party Client Guide

Everything a native (or any non-web) client needs to talk to the Vastukosh
GraphQL API. The web storefront and the mobile app are peers — they use the same
endpoint, schema and auth model; the only difference is how the refresh token is
stored (cookie for web, client-managed for native).

- **One endpoint:** `POST {BASE_URL}/graphql`
- **Schema contract:** [`../schema.graphql`](../schema.graphql) (committed, regenerated by `npm run print-schema`)
- **Transport:** JSON over HTTPS. No file uploads, no subscriptions.

---

## 1. Environments

| Environment | Base URL | Notes |
| ----------- | -------- | ----- |
| Local dev   | `http://localhost:4000` | Apollo Sandbox served at `/graphql` in a browser; introspection **on** |
| Staging     | _set per deployment_ | introspection on |
| Production  | _set per deployment_ | introspection **off**, landing page disabled |

Health check: `GET /healthz` → `200` with `{ "status": "ok" }` (also reports DB
connectivity). Use it for readiness probes, not as an auth check.

**Rate limiting.** `POST /graphql` is limited per IP: **120 requests / minute** in
production (1000/min in dev). Exceeding it returns HTTP `429`; back off and retry.

**CORS** only affects browsers. Native clients are unaffected. If you build a web
client on another origin, it must be added to `CORS_ORIGINS` on the server.

## 2. Generating a typed client

Point your codegen at `schema.graphql`. It is sorted and stable; commit a copy in
your app repo and refresh it when the backend publishes a new one.

**Apollo Kotlin (Android)** — `build.gradle.kts`:

```kotlin
apollo {
  service("vastukosh") {
    packageName.set("com.vastukosh.api")
    schemaFiles.setFrom(file("src/main/graphql/schema.graphql"))
  }
}
```

**Apollo iOS (Swift)** — `apollo-codegen-config.json`:

```json
{
  "schemaNamespace": "VastukoshAPI",
  "input": { "schemaSearchPaths": ["schema.graphql"], "operationSearchPaths": ["**/*.graphql"] },
  "output": { "testMocks": { "none": {} }, "schemaTypes": { "path": "./Generated", "moduleType": { "swiftPackageManager": {} } } }
}
```

**Flutter / Dart** — `build.yaml` with `graphql_codegen`, `schema: schema.graphql`.

The custom scalars are `DateTime` (RFC 3339 UTC string) and `JSON` (arbitrary
JSON value). Map `DateTime` to your platform date type and `JSON` to a dynamic
map.

## 3. Authentication

Token-based, client-agnostic. **Native clients store both tokens themselves.**

| Token         | Lifetime | Where it goes |
| ------------- | -------- | ------------- |
| Access token  | 15 min   | `Authorization: Bearer <accessToken>` on every request |
| Refresh token | 30 days  | Kept by the client; sent only to `refreshToken` / `logout` |

`signup`, `login` and `refreshToken` all return an **`AuthPayload`**:

```graphql
type AuthPayload {
  user: User
  accessToken: String
  refreshToken: String
  accessTokenExpiresIn: Int        # seconds (900)
  refreshTokenExpiresAt: DateTime
}
```

> The web client additionally receives the refresh token in an httpOnly `vk_rt`
> cookie and may call `refreshToken` / `logout` with no argument. **Native clients
> must pass `refreshToken:` explicitly.**

### 3.1 Sign up / log in

```graphql
mutation Login($input: LoginInput!) {
  login(input: $input) {
    accessToken refreshToken accessTokenExpiresIn refreshTokenExpiresAt
    user { id name email roles }
  }
}
# variables: { "input": { "email": "a@b.com", "password": "secret123",
#                          "anonId": "<guest-cart-id or omit>" } }
```

`SignupInput` additionally takes `name` (required), `phone`, `referredBy`.
Passing the guest `anonId` merges that guest's cart into the new account.

### 3.2 Refresh (rotation + reuse detection)

```graphql
mutation Refresh($rt: String!) {
  refreshToken(refreshToken: $rt) {
    accessToken refreshToken refreshTokenExpiresAt
  }
}
```

Every refresh **rotates** the token: the response carries a *new* refresh token,
and the old one is now invalid — replace your stored copy. If a already-used
(revoked) refresh token is presented, the **entire token family is revoked**
(stolen-token mitigation) and the call fails with `UNAUTHENTICATED`; the user must
log in again.

### 3.3 Recommended client flow

1. Attach `Authorization: Bearer <accessToken>` to every operation.
2. On a response whose `errors[].extensions.code == "UNAUTHENTICATED"`, call
   `refreshToken` **once**, store the new pair, and retry the original operation.
3. If the refresh itself fails → clear tokens, route to login.
4. Refresh proactively when `accessTokenExpiresIn` is close to elapsing to avoid
   the retry round-trip.

### 3.4 Log out

```graphql
mutation Logout($rt: String!, $everywhere: Boolean) {
  logout(refreshToken: $rt, everywhere: $everywhere)   # Boolean
}
```

`everywhere: true` revokes every session for the user.

## 4. Localisation

Send `x-locale: en` or `x-locale: hi` as a request header (default `en`). It
affects server-side localisation (e.g. error copy, SEO resolution).

Bilingual content is returned as a **`LocalizedString { en hi }`** — the client
picks the field for the active locale. Example:

```graphql
product(slug: "sacred-crystal-ganesha") {
  name { en hi }
  description { en hi }
}
```

## 5. Errors

GraphQL errors carry a stable machine code in `extensions.code` and an HTTP-style
status in `extensions.http.status`:

| `extensions.code` | status | Meaning |
| ----------------- | ------ | ------- |
| `BAD_INPUT`       | 400 | Validation / malformed argument |
| `UNAUTHENTICATED` | 401 | Missing/expired access token, or refresh reuse |
| `FORBIDDEN`       | 403 | Authenticated but not allowed (e.g. non-admin) |
| `NOT_FOUND`       | 404 | Entity does not exist |
| `CONFLICT`        | 409 | State conflict (e.g. illegal order transition) |
| `RATE_LIMITED`    | 429 | Too many requests |
| `INTERNAL`        | 500 | Unexpected — message is masked in production |

Validation failures from the schema layer may also appear as
`GRAPHQL_VALIDATION_FAILED` / `BAD_USER_INPUT`. Treat any unknown code as a
non-retryable client error except `INTERNAL` / `RATE_LIMITED`.

Transport errors (HTTP `429`, `5xx`, network) are separate from GraphQL `errors`
and should use your normal retry/backoff.

## 6. Guests vs. authenticated users

Cart and checkout work without an account by passing a client-generated
**`anonId`** (any stable random string) to the cart/order operations. On
`login` / `signup`, pass the same `anonId` to merge the guest cart into the
account. After that, omit `anonId` and rely on the bearer token.

## 7. Pagination

Catalog listing is offset-based:

```graphql
products(filter: ProductFilterInput, limit: Int, offset: Int, sort: ProductSort) {
  items { ... }
  total
  hasMore
}
```

`ProductSort`: `recommended | newest | price_asc | price_desc | rating`.
`ProductFilterInput`: `{ category, need, rashi, featured, search }`.

## 9. Panchang

`@vastukosh/panchang` (a standalone package in this repo, `packages/panchang`)
computes the five aṅgas plus sun/moon rise & set, the lunar month, season, samvat
years, sidereal signs, and the day's kālas. Values are **almanac-grade
approximations** (Meeus algorithms, mean Lahiri ayanāṁśa) — good for display and
muhūrta hints, not certified panchāṅga.

All arguments are optional. Unset `latitude`/`longitude`/`timezone` fall back to
the server default (New Delhi, `Asia/Kolkata`). `date` is `yyyy-mm-dd` in
`timezone`; omit for today. `monthSystem` is `amanta` (default) or `purnimanta`.

```graphql
query TodayPanchang($date: String, $lat: Float, $lng: Float) {
  panchang(date: $date, latitude: $lat, longitude: $lng, timezone: "Asia/Kolkata") {
    date
    location { latitude longitude place }
    sunrise sunset nextSunrise solarNoon moonrise moonset
    ayanamsa
    vara      { index name { en hi } start end }
    tithi     { index name { en hi } start end fractionElapsed }
    nakshatra { index name { en hi } start end pada lord }
    yoga      { index name { en hi } start end }
    karana    { index name { en hi } start end }
    paksha { en hi }
    masa { en hi }  masaAmanta { en hi }  masaPurnimanta { en hi }
    ritu { en hi }
    vikramSamvat shakaSamvat
    sunSign { en hi }  moonSign { en hi }
    auspiciousPeriods  { name { en hi } start end quality }   # Brahma & Abhijit Muhurta
    inauspiciousPeriods { name { en hi } start end quality }  # Rahu Kala, Yamaganda, Gulika Kala
  }
}
```

Sample response (New Delhi, 2024-11-01 — Diwali):

```json
{
  "data": { "panchang": {
    "date": "2024-11-01",
    "sunrise": "2024-11-01T01:03:18.338Z",
    "tithi": { "index": 30, "name": { "en": "Amavasya", "hi": "अमावस्या" },
               "end": "2024-11-01T12:47:43.373Z" },
    "nakshatra": { "index": 15, "name": { "en": "Swati" }, "pada": 1, "lord": "Rahu" },
    "paksha": { "en": "Krishna Paksha", "hi": "कृष्ण पक्ष" },
    "masaAmanta": { "en": "Ashwina" }, "masaPurnimanta": { "en": "Kartika" },
    "vikramSamvat": 2081, "shakaSamvat": 1946
  } }
}
```

Each aṅga's `name.en` is a romanised form and `name.hi` is Devanāgarī — reuse the
`LocalizedString` handling from §4. All timestamps are UTC (`DateTime`).

**Limitations:** adhika/kṣaya months are not modelled; samvat years use a civil
approximation for the new-year rollover; Varjyam/Amṛta Kāla/Durmuhūrtam are not
returned; polar latitudes error with `BAD_INPUT`.

## 10. Payments

`placeOrder` returns `PlaceOrderResult { order, clientData }`. With the default
`mock` provider the order auto-confirms and `clientData` is null — good for
development. With `razorpay`, `clientData` carries the fields your client needs to
open the Razorpay checkout SDK; on success the backend is notified via a
server-to-server webhook (`POST /webhooks/razorpay`, HMAC-verified). **Switching
providers does not change the schema**, so build against `placeOrder` /
`clientData` and treat `clientData` as an opaque provider payload.

## 11. Examples

**curl**

```bash
curl -s https://api.example.com/graphql \
  -H 'content-type: application/json' \
  -H 'authorization: Bearer <accessToken>' \
  -H 'x-locale: hi' \
  -d '{"query":"{ me { id name email } }"}'
```

```kotlin
val response = apolloClient.query(TodayPanchangQuery(date = Optional.presentIfNotNull(null))).execute()
val tithi = response.data?.panchang?.tithi?.name?.hi
```

**Swift (Apollo)**

```swift
apollo.fetch(query: MeQuery()) { result in
  guard case .success(let gql) = result, let user = gql.data?.me else { return }
  print(user.name ?? "")
}
```

## 12. Versioning

The schema evolves additively. Breaking changes (field removals, type changes)
are announced and staged; regenerate your client from the updated
`schema.graphql` when notified. There is no URL version segment — the SDL file is
the contract. Track the backend `CHANGELOG` / release notes for schema deltas.
